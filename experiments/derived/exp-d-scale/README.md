# Experiment D-scale: one concurrency-8 level and scaling of graph-evidence-api (window 3, exp-d-scale-v1)

Generated by experiments/analysis/derive-tables.py from the sources listed below.

Expected finding (manifest exp-d-scale-v1): one scale-out and one scale-in at the 15 percent CPU target, and no throughput gain from the second task while Neptune is the bottleneck. Compare the steady-state rows of throughput-steady-state.csv (not only the phase averages in throughput-by-task-count.csv) and neptune_cpu in metrics-per-minute.csv, with the caveats below. The CPU target of 15 percent is an experiment setting (Phase 15 ruling 2), not a production value.

Caveats (code review 3, E-m4; Phase 15 ruling 12(e)):

- The one-task phase includes the level's warm-up. ALB requests per minute (UTC minute, count) during the level: 00:19 1546, 00:20 1856, 00:21 2106, 00:22 2217, 00:23 2241, 00:24 2324, 00:25 2364, 00:26 2398, 00:27 2422, 00:28 2472, 00:29 16; the second target registered at 2026-11-20T00:24:32.269Z. The rise began before the second task, so the phase averages in throughput-by-task-count.csv overstate the gain from the second task; compare the steady-state rows instead.
- A warmed single task at concurrency 8 already served 35.72 requests per second in window 2 (the reference row of throughput-steady-state.csv, level start 2026-11-18T06:49:46.583Z).
- Neptune CPU (1-minute average) was 97.0 to 98.7 percent in every full level minute after the first, in both phases: Neptune stayed saturated with one task and with two.
- The split uses the ECS 'registered 1 targets' event. Registration is not health: the ALB routes to the new target only after it passes health checks, which the events do not time (alb_healthy_* in metrics-per-minute.csv are 1-minute samples).
